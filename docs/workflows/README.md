# Workflows

Generated by `python -m wf docs` from tools/wf; do not edit by hand.

| Workflow | Burr UI project | What it is for |
|---|---|---|
| [verify](verify.md) | recomp-verify | Verify the main checkout (docs/PROCESS.md §3): lift and build, difftest the changed functions against their lifted originals on random inputs and on the original game's captured calls, run them on the CPU oracle, replay every recorded route in lockstep, and the battle sweep when battle code changed. |
| [capture](capture.md) | recomp-capture | Capture the original game's own calls of some functions (the inputs that difftest and the CPU oracle check conversions on): give each function a recorded route that executes it (as few routes as possible), replay those routes on the original in parallel, save the first calls of each function. |
| [farm](farm.md) | recomp-farm | Outside models convert small lifted functions in volume (docs/PROCESS.md §4). One `farm` run is one function and one model: the model writes readable C, the farm's acceptance test checks it against the lifted original on the captured calls and random inputs, failures go back to the model for repair, and an accepted function gets its symbols/db entry drafted by the same model. A `farm batch` run builds the host difftest once, skips pairs that are already finished, and runs the rest as its child runs. |
| [farm-batch](farm-batch.md) | recomp-farm | Outside models convert small lifted functions in volume (docs/PROCESS.md §4). One `farm` run is one function and one model: the model writes readable C, the farm's acceptance test checks it against the lifted original on the captured calls and random inputs, failures go back to the model for repair, and an accepted function gets its symbols/db entry drafted by the same model. A `farm batch` run builds the host difftest once, skips pairs that are already finished, and runs the rest as its child runs. |
| [drafts](drafts.md) | recomp-drafts | A farm model drafts the symbols/db entries of its accepted candidates that have none yet (tools/convert/accepted/NAME.MODEL.yaml), in parallel: the documentation small functions bring into the convert workflow's review and record. New farm runs draft as they accept; this catches up older ones. |
| [convert](convert.md) | recomp-convert | A strong outside model converts a subsystem (callers and callees together) to readable C with C call and return semantics (docs/PROCESS.md §4): capture the original's calls, ask the model for the whole file, check it keeps guest registers to thin adapters (tools/abi/lint.py), quick-test it per function against the lifted originals, install it and run the full verify, then stop for the orchestrator's review. Failures and review comments go back to the model (3 attempts per model, then the next model). A group of farm candidates goes the same way, except that failing functions are taken out of it (they stay in the farm's pool) instead of going to a model. Approved work is committed, its symbols/db entries are written from the model's drafts plus the run's own evidence, and a child record run renames and documents it. The orchestrator never writes the code: it chooses the work and reviews. |
| [record](record.md) | recomp-record | Put what was learnt about symbols into the symbol database and the disassembly (docs/PROCESS.md §6, and the user's rule: every discovery goes into bn6f and symbols/db with evidence and how to reproduce it). |
