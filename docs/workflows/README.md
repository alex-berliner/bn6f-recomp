# Workflows

Generated by `python -m wf docs` from tools/wf; do not edit by hand.

| Workflow | Burr UI project | What it is for |
|---|---|---|
| [verify](verify.md) | recomp-verify | Verify the main checkout (docs/PROCESS.md §3): lift and build, difftest the changed functions against their lifted originals on random inputs and on the original game's captured calls, run them on the CPU oracle, replay every recorded route in lockstep, and the battle sweep when battle code changed. |
| [capture](capture.md) | recomp-capture | Capture the original game's own calls of some functions (the inputs that difftest and the CPU oracle check conversions on): give each function a recorded route that executes it (as few routes as possible), replay those routes on the original in parallel, save the first calls of each function. The calls go into the snapshot store, build-snapshots/FUNCTION, next to what earlier captures saved there: one file per call, named by its route, and a replay is deterministic, so capturing on a route again writes the same files. |
| [farm](farm.md) | recomp-farm | Outside models convert small lifted functions in volume (docs/PROCESS.md §4). One `farm` run is one function and one model: the model writes readable C, the farm's acceptance test checks it against the lifted original on the captured calls and random inputs, failures go back to the model for repair. `--prompt old` asks with the prompt before the typed one (register-form C, no register check; docs/reviews/2026-10-10-benchmark.md): its rounds and candidates are filed under the model tagged `+old` (FUNC.minimax_MiniMax-M3+old.c), a pair of its own. With the typed prompt (typed-2), a round starts from the best attempt so far, another model's included (the hand-over, wf/tools/handover.py), and a passing candidate is kept with the generated wrappers it calls. (Entries for accepted functions are drafted afterwards by `wf drafts --drafter`, on a plan's quota rather than the farm model's.) Earlier: an accepted function got its symbols/db entry drafted by the same model. A `farm batch` run builds the host difftest once, skips pairs that are already finished, and runs the rest as its child runs. |
| [farm-batch](farm-batch.md) | recomp-farm | Outside models convert small lifted functions in volume (docs/PROCESS.md §4). One `farm` run is one function and one model: the model writes readable C, the farm's acceptance test checks it against the lifted original on the captured calls and random inputs, failures go back to the model for repair. `--prompt old` asks with the prompt before the typed one (register-form C, no register check; docs/reviews/2026-10-10-benchmark.md): its rounds and candidates are filed under the model tagged `+old` (FUNC.minimax_MiniMax-M3+old.c), a pair of its own. With the typed prompt (typed-2), a round starts from the best attempt so far, another model's included (the hand-over, wf/tools/handover.py), and a passing candidate is kept with the generated wrappers it calls. (Entries for accepted functions are drafted afterwards by `wf drafts --drafter`, on a plan's quota rather than the farm model's.) Earlier: an accepted function got its symbols/db entry drafted by the same model. A `farm batch` run builds the host difftest once, skips pairs that are already finished, and runs the rest as its child runs. |
| [queue](queue.md) | recomp-queue | The shared work queue (review 3 Area 5.3-5): one long run that keeps every provider with quota busy on the functions left to farm (captured calls, no passing candidate), each routed by its size to one prompt and an order of models (wf/tools/work_queue.py ROUTES: the old prompt at 11-30 lines, MiniMax-M3 first; the typed prompt elsewhere). Each provider has a lane of workers. A worker takes the next job whose next model is its provider's (or, rather than idle, one where its model comes later), runs one farm run on it (one round plus one repair, review 3 Area 2; runaways are stopped at their reasoning budget) and records the result in the jobs' ledger, build-wf-state/queue-jobs.json, which every queue run shares. A job keeps its prompt version, and ends when a candidate passes, every model of its route has tried, or it has spent its token cap. A provider that is down (rate limit, spent credit, wf/tools/sources.py) takes no jobs until it is back; Hyper's lane starts again at its daily reset. Functions other farms are on (their `wf farm` arguments) are left alone. A shift ends every few hours: the difftest is rebuilt from the last commit and the work planned again. `wf queue --stop` (or SIGTERM) lets the farm runs under way finish and ends the run. |
| [drafts](drafts.md) | recomp-drafts | A farm model drafts the symbols/db entries of its accepted candidates that have none yet (tools/convert/accepted/NAME.MODEL.yaml), in parallel: the documentation small functions bring into the convert workflow's review and record. New farm runs draft as they accept; this catches up older ones. |
| [convert](convert.md) | recomp-convert | A strong outside model converts a subsystem (callers and callees together) to readable C with C call and return semantics (docs/PROCESS.md §4): capture the original's calls, ask the model for the whole file, check it keeps guest registers to thin adapters (tools/abi/lint.py), quick-test it per function against the lifted originals, install it and run the full verify, then stop for the orchestrator's review. Failures and review comments go back to the model (3 attempts per model, then the next model). A group of farm candidates goes the same way, except that failing functions are taken out of it (they stay in the farm's pool) instead of going to a model, and its file is an inbox: each function goes to the file of its bn6f source (tools/layout.py), where the verify builds and the commit puts it; a candidate accepted before the farm drafted symbols/db entries gets its entry drafted first (`wf drafts`' step). A group of the farm's old-prompt candidates (`--farm-model MODEL+old`) may keep register-form code: the register check is shown at review but does not stop it, and its commit queues each function with register-level code for retype (tools/abi/retype_queue.tsv) and raises the lint baseline by exactly their hits (tools/wf/wf/tools/retype.py). Approved work is committed, its symbols/db entries are written from the model's drafts plus the run's own evidence, and a child record run renames and documents it. The orchestrator never writes the code: it chooses the work and reviews. |
| [record](record.md) | recomp-record | Put what was learnt about symbols into the symbol database and the disassembly (docs/PROCESS.md §6, and the user's rule: every discovery goes into bn6f and symbols/db with evidence and how to reproduce it). |
| [vidsync-run](vidsync-run.md) | recomp-vidsync | Keep the vidsync sync going on the compute PCs (docs/vidsync/README.md): deploy this checkout's vidsync to both PCs, restart the worker server and the driver from a checkpoint, then watch the driver's progress, the furthest game frame its logs reached. Every hour the path so far is replayed against the video (pathcheck); when it does not hold, the driver restarts from a clean checkpoint before its first loss. When the furthest frame has not moved for 30 minutes (stuck: not log silence, the driver logs while it searches), or the driver gave up at a loss, a vidsync-repair run is opened for that loss. Without --start the running driver is only watched; --watch-hours ends the watch after that long whatever happens. |
| [vidsync-repair](vidsync-repair.md) | recomp-vidsync | A new repair handler for a loss the vidsync driver could not get past (docs/vidsync/README.md). The loss is rendered with the probes (the emulator beside the video, and the video after it) on the driver PC; Claude looks and says what differs and which symbols and routines matter; an outside model writes the handler from a brief carrying the symbols/db entries and the routines' assembly; Claude reviews it; it is tested from the loss checkpoint (it must sync 600 frames past the loss on the driver PC's own workers, and the path must then hold against the video). What was learnt about the game goes into symbols/db and bn6f through `record`; the handler is committed, deployed, and the driver restarts past the loss. |
| [vidsync-ready](vidsync-ready.md) | recomp-vidsync | Turn the vidsync sync's newest checkpoint into the `beastsp` route (docs/vidsync/README.md): on the driver PC, export it as a route-harness recording verified with mgba_run, and cut it into save-file segments (one about every 20,000 game frames, each checked equal to the run); check the segments; copy the recording and the segments here (build-vidsync/ready). With --import, tools/import_route.py brings it into tools/traces/beastsp.* (checkpoints, profiles, coverage, the route's length) and the port is lockstepped on the longer route; the import replays the whole route here, so it is asked for, not the default. |

It reads the driver's state and the log around the loss it is on (remote/digest.py), and sorts it (wf/tools/vidsync_triage.py): |
| [facts](facts.md) | recomp-facts | `wf facts`: the runtime-facts layer -- a record of what the original game did at runtime for every lifted function, made entirely from the project's own recordings and captures and never from a model: per-route coverage from the route profiles and call-edge files, and for the functions build-snapshots holds calls of, the replayed arguments and returns and the full RuntimeFacts block. Writes one JSON per function under build/facts/by_address/ (keyed by address, so a rename never loses it), a coverage.tsv row per function, and progress.txt; rebuilds only what moved.
