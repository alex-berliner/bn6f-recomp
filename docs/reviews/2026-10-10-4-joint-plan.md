Terms used below:
- **Lifted C:** the exact but unreadable C the lifter makes from the ROM.
- **Contract:** which registers a function reads and which it returns.
- **Stamp:** a short record per readable function saying what it was made from (details in Section 2, S1).
- **Commit gate:** the checks that must pass before a commit is accepted.
- **Golden tests:** saved lifter output that any lifter change is compared against.
- **Codemod:** a script that rewrites many functions at once.
- **Typify:** a tool that turns a register-form body into typed C.
- **Retype:** a model doing the same job where the tool can't.
- **Install freeze:** installs and commits pause while models keep producing candidates.
- **Runaway:** a model reply that spends its whole output budget on hidden reasoning and returns no code.

## 1. Summary

The stages:
- **S0, today and tomorrow:** use the quota that is about to expire (MiniMax ends 10-13; Hyper's credit is lost daily at 10:13). Make the small pipeline fixes. Re-test about 2,800 saved candidates for free.
- **S1, foundations (about 4 days):** a ledger of farm results, a stamp on every function, the safety fixes, the commit gate, golden tests, faster builds, the db rewrite and the regroup.
- **S2, cheaper model work (about 4 days, alongside S1):**
  - stop runaways mid-reply and shorten repair chains;
  - fix the failure reports models get;
  - run the benchmark and make one measured prompt change;
  - then one shared work queue for all providers.
- **S3, mechanical typed C (about 1.5 weeks):** tools, not models, rewrite as much register form as they can.
- **S4, retype (about 3 days of setup, then ongoing):** models finish what the tools couldn't, from the shared queue.
- **S5, background:** hygiene, docs, extra checks, at quiet moments.

**The regenerability question.** Is the chain of continuity from the lifted output lost?
- **Behaviour:** no. Every readable function is checked against the lifted code, and the lifted code matches the ROM.
- **Origin:** partly. The 1,435 functions were written under changing rules and prompts, mostly by one model (about 1,360 by glm-5.3-flash, about 40 by hand), and nothing records what each one was made from.
- **Recommendation:**
  - The "one-shot method" is the pipeline: lift, then tools, then models, then verify. It could be rerun on any lifted output.
  - Make "regenerable" an explicit but limited goal, in three promises:
    1. whatever a tool wrote is rebuilt by the tool;
    2. whatever a model wrote is replayable from its saved reply and stamped;
    3. hand edits are recorded.
  - Do not turn `cport/src/game` into pure build output. Model replies can't be re-derived, so that only adds a copy.
  - Cost: about 1-1.5 days. It goes before any more mass rewriting.

### S1. Foundations (about 4 days, in install-freeze windows)

Items:
- **Ledger and cost:**
  - `pool.py` and `pool.tsv` (R1-A1), with oracle-drop triage (R1-A2);
  - cost per installed function in each plan's own units, time to first byte, one identity per model (R3-Area6.2, R3-B29/B44).
- **The stamp and its check (new; this answers the regenerability question).** One record per function in its db entry. Fields:
  - ROM bytes hash and address range;
  - own contract and callees' contracts;
  - headers hash, prompt hash, model, run, lifter version;
  - installed-body hash and install commit.

  `symdb check` then applies a fixed action to each change:

  | What changed | Action |
  |---|---|
  | Own outputs widened, or the bytes/range changed | Back to a model |
  | Own outputs narrowed | Re-verify, and queue the dead writes for removal (R1-A6) |
  | A callee narrowed and the R1-A21 lint flags this caller | Re-verify |
  | Headers | Recompile and re-verify |
  | Body changed without a record | Re-stamp as a hand edit |
  | Prompt or lifter version | Informational only; golden tests and lockstep cover lifter changes |

  The 1,435 existing functions get stamps computed now, with prompt marked "legacy". No re-farming.
- **Safety:**
  - the `g_cfg[256]` overflow (R1-B33);
  - the leftover-register lint and its 31 call sites (R1-A21);
  - the ROM read-only on the host (R1-Area3.4);
  - refined contracts (R1-A7).
- **Gate:**
  - the rename tool updates the lint baseline, with readable rename commit subjects (R2-A20, R2-A10);
  - then the commit gate with the 1-second symdb check (R1-Area8.2, B13).
  - The gate reruns only generators: golden tests, `gen.py`, equates, `gen_structs`, `SYMBOLS.md`, `pool.tsv`, the stamp check and the layout check. It makes no model calls and runs no lockstep.
- **Lifter and builds:**
  - golden tests and `.edges` files (R1-B22/B34);
  - lifter environment switches become flags (R2-Area4.5);
  - build speed (R1-Area5.1-4);
  - the lockstep digest cache, one bn6f build per record run, and skipping the reverify when the ROM is unchanged (R1-Area6.1/6.3, A27/B25).
- **Shared paths:**
  - `tools/paths.env`, written as a per-game profile (R2-Area2);
  - a build rule for `mgba_run`;
  - the BIOS moves to `roms/`, and `build/abi/graph.json` moves out of the PC port's folder (R2-Area3.5 step 1).
- **db and layout:**

## 3. Conflicts between the reviews, and how they were settled

**Between the reviews:**
- **Cleaning `build-wf-runs` (R1-Area8.1) vs R2-Area1:** R2 wins. 56 GB of it is the live farm's input. Only the R2 steps run.
- **R1's attic folder vs R2's cited-by scanner (delete, with a restore note):** R2 wins.
- **Fixing the dead `/tmp` reproduce lines** (R1-Area6.6 snapshot key vs R2-Area6 per-function commands): R2's form now. R1's form only if the content store is ever built.
- **The commit gate vs the rename tool:** R2-A20 lands first, or the first rename breaks the gate.
- **Two re-tests** (R1: 221 pending; R3: ~2,600 failed): one `pool.py retest` run writing one ledger.
- **Adapters** (R1's typify writes signatures at install; R3's `gen.py` prefills a signature line): one generator, signature blocks written at install, helpers as build-time headers.
- **Reference files** (R2: drop both; R3: replace them): drop both and add one short example, inside the benchmarked prompt change.
- **`farm.py`** (R2 deletes the driver; R3 edits its test and prompt): the library stays, the driver goes. Prompt changes are tracked by the prompt hash.
- **Quiet points** (R1 and R2 need them; R3's always-on queue removes them):
  - the structural moves (db rewrite, regroup, header split, `paths.env`) land in S1 install-freeze windows, before the queue goes always-on;
  - the natural window is Hyper's out-of-credit hours before 10:13;
  - no quiet day and no farm stop.
- **Cleaning `~/.burr` (R2-Area1.6) would lose the only copy of the drop reasons:** it waits for the ledger backfill.

**Between the debaters:**
- **Unit store and assembler (rebuilding `cport/src/game` from stored per-function pieces).**
  - A proposed it, B rejected it. In round 2 they swapped sides; in round 3 both rejected it.
  - Deciding fact: everything a store would hold is already in the tree and the db. The stamp's body hash catches unrecorded hand edits. The layout check catches misplaced functions.
  - A store would also force every code-writing tool (install, rename, drop, bisect, all codemods) to change, and would cost about a week or more.
- **Staleness key.** B first proposed a hash of the lifted C. A showed that every rename and lifter pass changes it: R1-A22 alone touches 510 aliases and 1,870 numbers. So the key is the original ROM bytes, and contract changes are a separate trigger with the actions in S1.
- **Prompt by size band.** B's early lean (typed up to 30 instructions, old prompt plus retype above) was withdrawn. The thin data point the other way: typed costs about 3x at 11-30 instructions and about 1x at 31-60. Typed stays the default until the benchmark reports.
- **`UNSEEN_SITES.md`.** A first wanted to delete it; it is kept as the recording list.
- **Moderator's calls on placement:**
  - the PC-port deletion goes to S5, and its prerequisites (BIOS, `graph.json`) to S1;
  - reusing the main tree's difftest and the forced-edge check go to S5;
  - `build_bn6f.sh` goes with the PC-port removal;
  - the mutation survey opens S3.

## 6. Appendix: the drafts and how the debate moved them

**A's first draft:**
- A unit store plus assembler: `cport/src/game` rebuilt from (bn6f commit, lifter, recipe), with a gate check that the rebuild reproduces the tree.
- The cache keyed on ROM bytes plus contract.
- Safety, gate, build speed and PC-port removal in S1; provenance and the store in S2; pipeline fixes in parallel.
- Delete `UNSEEN_SITES.md`.
- Estimated cost 3-5 days.

**B's first draft:**
- "Partial" regenerability as three promises: tools regenerate; model output is replayable and stamped; hand edits are recorded.
- Stamps keyed on a lifted-C hash; about 1 day.
- Pure build output rejected as "the tree with extra steps" that fights the codemods.
- Golden tests and build speed late (S3).
- A declared quiet day.
- A lean of typed prompt up to 30 instructions.

**Round 2: they swapped sides.**
- A dropped the store and took B's promises, but:
  - showed the lifted-C hash would flag everything;
  - moved golden tests to S1, since the build-speed work edits the lifter's output;
  - replaced the quiet day with install freezes;
  - pointed out B's typed lean was one R3 had already withdrawn.
- B adopted the store, but only with current bodies plus a list of the passes applied, and contracts as a trigger rather than a key.

**Round 3: both rejected the store.**
- B: a body hash in the stamp catches unrecorded edits, the only thing the store added.
- A: every field is already in the tree or the db; the layout check gives the placement guarantee.
- A added the callee-narrowing rule: a callee's output shrinking can break a caller, R1-A21's bug class.
- B conceded the size-band lean.
- They combined the freeze windows with "structural moves before the always-on queue".

**Round 4 (omissions):** both placed every remaining item from the three reviews (Sections 2 and 4). They differed only on where four small items go, settled in Section 3.
